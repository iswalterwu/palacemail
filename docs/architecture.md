# PalaceMail 技术选型与架构设计

> 草案 v0.1（2026-10-16），供评审。本文只给推荐，不穷举方案；每条决策附理由，日后推翻时有据可依。

## 1. 目标与约束

- **目标**：本地优先的邮箱客户端。内核按"AI 能高效读取、理解、执行"来组织数据与流程，界面安静、清晰、顺手。
- **约束**：开源、小团队起步、不自建服务器；邮件与密钥留在用户设备；同时支持国内外多家模型供应商与本地模型；东方风格视觉后置，只预留扩展点。
- **"AI 处理效率"的定义**：同一任务用更少的 token、更低的延迟与成本完成；中间结果可复用、可重算；上下文组装是确定性的，而非每次临场拼凑。

## 2. 技术选型

| 领域 | 推荐 | 备选 | 理由 |
|---|---|---|---|
| 客户端形态 | 桌面优先：Tauri 2；内核设计为可脱离界面运行的库 | Electron；Web + 自建后端 | 数据与密钥留在本机，零服务器成本；同一内核日后可作守护进程支撑自托管 Web 模式 |
| UI 框架 | React + TypeScript + Vite | Vue 3；Svelte 5 | 长列表虚拟化、富文本编辑（TipTap）、无障碍组件生态最成熟；内核不依赖具体框架 |
| 本地服务 | Rust 内核 `palace-core`，与界面同进程、无独立后端；经 Tauri IPC 暴露类型化命令与事件（tauri-specta 生成 TS 绑定） | Node 内核 + Electron | 内存占用低、并发安全；Delta Chat、Stalwart 已验证 Rust 邮件栈（async-imap、mail-parser、mail-send）可用于生产 |
| 存储与索引 | 单个 SQLite 库：结构化表 + FTS5 全文 + sqlite-vec 向量；原始 MIME 与附件按内容哈希落盘 | Tantivy；LanceDB | 一个文件、一个事务边界，混合检索一条 SQL 完成；中文由内核用 jieba-rs 预分词后写入 FTS，绕开 FTS5 trigram 分词器只支持三字以上查询的限制 |
| AI 接入 | 内核内置供应商抽象，只适配两种线协议：OpenAI 兼容（DeepSeek、通义、Kimi、智谱、Ollama 等）与 Anthropic Messages；配置按"角色"而非型号 | rig、genai 等 Rust 框架 | 两种协议覆盖绝大多数云端与本地供应商；薄适配层可控、无锁定 |

**取舍说明**：Rust 起步慢于 TypeScript，WebView 在三平台有差异，用这两项成本换取更低的资源占用、更强的安全性与"内核即服务"的可能；若团队更熟悉 TS，可在 Electron + Node 上实现完全相同的模块边界。sqlite-vec 仍年轻、目前只做暴力检索，但十万级邮件配合元数据预过滤足够，向量存储接口保持极薄以便替换。

## 3. 模块划分与数据流

四层单向依赖，上层只认下层的接口，所有跨层数据类型由 store 定义：

```
ui（React）     视图模型 · 设计令牌与主题 · 助手面板
   │  查询 / 命令 / 事件（Tauri IPC，类型化）
assistant      供应商抽象 · 提示词注册表 · 上下文组装 · 摘要/分类/检索/起草流水线
   │  读规范化数据，写派生数据与动作提议
store          唯一事实来源：规范化消息 · 会话 · 联系人 · FTS · 向量 · 派生数据 · 作业队列
   │  原始消息入库 / 出站动作
mail           IMAP/SMTP 适配 · OAuth · 增量同步 · 出站队列
```

- **入站流**：mail 拉取原始消息 → store 在一个事务内解析为规范化消息并更新会话、联系人统计与全文索引 → 入队作业（嵌入、分类、摘要）→ assistant 按优先级消费，结果写回派生表 → store 发出变更事件 → ui 增量刷新。
- **出站流**：ui 或 assistant 产生动作（归档、打标、发送草稿）→ 统一命令层校验、乐观写入 store → mail 异步同步到服务器，失败回滚并通知。
- **边界规则**：ui 不直接调用模型；assistant 不碰 IMAP；mail 不知道 AI 的存在。
- **界面原则**：AI 结果以安静的建议呈现（分类标签、摘要行、建议回复），助手面板是补充入口而非主入口；界面不自行拼装提示词。

仓库按模块组织：`apps/desktop`（Tauri 壳与界面）、`crates/core`（对外 API）、`crates/mail`、`crates/store`、`crates/assistant`、`packages/ui`（组件与设计令牌）。

## 4. 关键设计决策与取舍

1. **一次解析，规范化存储，AI 永不读原始 MIME。** 入库时把 MIME 解析为结构化头部、干净正文（HTML 转 Markdown，剥离引用、签名、跟踪像素）、附件清单，并预估 token 数。解析与清洗是最大的重复开销，前置一次即可被所有任务复用；原件保留用于保真展示与导出。
2. **以会话为单位，分层表示。** 每条消息存三档粒度：snippet（约 200 字）、clean_text、可选 summary；会话维护去重后的增量摘要。上下文组装器按 token 预算从粗到细填充，结果可预测、可缓存。多数 AI 任务的对象是会话而非单封邮件，分层让"扫一眼"与"深读"用不同成本。
3. **AI 产物一律是派生数据。** 摘要、分类、实体、嵌入以（对象、任务、模型、提示词版本、输入哈希）为键存放，输入变化即失效，随时可重算；绝不与来自服务器的事实数据混存。模型与提示词会频繁更换，派生化让升级只是一次后台重算，也让每个输出可追溯。
4. **分级处理，按角色路由。** 先规则与统计（发件人互动频率、列表邮件识别），再小模型（`fast` 角色：分类、抽取），最后大模型（`smart` 角色：起草、复杂摘要）；嵌入走 `embed` 角色，可本地可云端。大多数邮件不值得调用大模型，分级把成本与延迟集中在真正需要的地方；配置写角色不写型号，换供应商不改代码。
5. **作业队列：可见优先、后台补齐、幂等。** 用户正在看的会话插队；初次同步先取近期头部，正文与历史后台补齐；每个阶段可重试、可中断。感知速度取决于当前视口而非全量完成度；限流与断网是常态。
6. **检索即工具。** store 提供混合检索（全文 + 向量 + 结构化过滤：人、时间、附件、标签），返回紧凑、已排序、有 token 上限的片段；内置助手与后续的外部代理（MCP）共用同一套工具定义。这是"AI 一等公民"最具体的落点，也避免每个功能各写一套查库逻辑。
7. **AI 只提议，内核执行。** 模型输出的动作先成为提议，经统一命令层校验后执行，全部记入动作日志并可撤销；发送邮件永远需要用户确认。安全边界放在内核而非提示词里，才经得起模型的不确定性。
8. **本地优先与隐私。** 密钥存操作系统钥匙串；模型请求由客户端直连供应商，不经任何 PalaceMail 中间服务；提供"哪些数据会离开本机"的明确开关。零服务器成本，隐私承诺可验证。
9. **界面层只预留主题扩展点。** 组件只消费设计令牌（色彩、字体、留白、动效节奏），主题即一组令牌；东方风格届时作为新主题加入，不改组件。

## 5. 阶段规划

**阶段一 · MVP：可日常使用的单账户客户端**

- 账户：通用 IMAP/SMTP，密码或授权码登录（覆盖 QQ、163、iCloud、Gmail 应用专用密码），密钥入钥匙串。
- 同步：文件夹增量同步（UIDVALIDITY、CONDSTORE、IDLE），离线可读；发送、回复、转发、归档、标记、删除。
- 内核：规范化入库、会话聚合、全文检索、作业队列、派生数据表。
- AI：配置一家 OpenAI 兼容或 Anthropic 供应商；会话摘要、收件箱分类（需回复 / 通知 / 订阅等）、带上下文的回复起草。
- 界面：三栏布局、命令面板、助手侧栏、明暗两套默认主题，设计令牌体系落地。
- 验收：一万封邮件的账户内，打开会话与搜索响应低于 200 ms，首屏不等待 AI；每个 AI 结果可追溯到模型与提示词版本。

**阶段二 · 多账户与 OAuth**：Gmail、Microsoft 365 的 OAuth 2.0（PKCE + 本地回环，Outlook 已不支持密码登录）；统一收件箱；向量索引与混合检索；内置本地嵌入模型（fastembed）。

**阶段三 · 代理化**：自然语言规则与自动化、待办与日程抽取、内核作为 MCP 服务对外开放、无头 CLI 与守护进程模式。

**阶段四 · 东方风格视觉系统与自托管 Web 模式**：主题、字体与动效体系；内核以守护进程运行、浏览器访问的部署形态。
